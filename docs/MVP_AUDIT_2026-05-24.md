# MVP audit - 2026-05-24

This audit is the baseline for getting the dedicated-server MVP stable before adding more features.

## External baseline

Primary references checked:

- Godot high-level multiplayer docs: https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html
- Godot ENetMultiplayerPeer docs: https://docs.godotengine.org/en/stable/classes/class_enetmultiplayerpeer.html
- Godot MultiplayerAPI docs: https://docs.godotengine.org/en/stable/classes/class_multiplayerapi.html
- Godot SceneTree docs: https://docs.godotengine.org/en/stable/classes/class_scenetree.html

Relevant rules from the docs:

- ENet in Godot is UDP-only for the public game port. Server port forwarding must be UDP.
- A client being connected is not the same as being ready to receive gameplay RPCs.
- Godot's lobby example explicitly has clients tell the server when their game scene has loaded; the server then starts gameplay after clients are loaded.
- Reliable RPC preserves order but has a performance penalty. Different reliable streams, chat, gameplay acks, snapshots, and fast unreliable updates should use channels when they grow.
- `multiplayer.get_remote_sender_id()` is the correct way to identify the RPC sender inside RPC handlers.
- Dedicated-server samples need to be adapted so the server is not treated as a normal player.

## Required invariants

These must stay true. If a future patch violates any item, the patch is unsafe.

1. Transport connected != gameplay joined.
   The client may only perform gameplay actions after:
   - server world snapshot applied,
   - local player exists,
   - persistent character restore or new profile fallback completed,
   - client state sent to the server,
   - server confirms that peer state is registered in the active dimension instance.

2. Server authoritative world.
   Client block, water, fire, storage, drop, pickup, entity, and player attack actions are requests. The server applies them, journals/persists them, then acks/syncs the result.

3. Locked client actions must be consumed.
   If the client is connected to a server but not gameplay-ready, hook functions must return `true` for world-mutating actions so vanilla singleplayer code cannot create unsynced local state.

4. UI/menu flags cannot be the only network readiness source.
   `Ref.main.loaded` is useful for vanilla UI state, but a server-loaded world can have valid `Ref.world` and `Ref.player` while `Ref.main.loaded` is stale. Network readiness must use explicit network flags.

5. Server save cache is not a playable singleplayer save.
   Client-side server-world cache must remain hidden/deleted in the singleplayer world list. Players join server worlds only through Co-op.

6. Persistence has two layers.
   - Character persistence: client sends persistent state to server, currently every `PERSIST_INTERVAL` while ready and on leave.
   - World persistence: successful server block/storage/dynamic cell actions must journal immediately; dirty chunks are compacted/flushed later.

7. Time/weather are server authority.
   Dedicated server must own time/weather. Clients should not independently drift weather/time after join.

8. Drops and mobs are interest-managed server state.
   Clients may show predictions for responsiveness, but pickup/drop final truth comes from server UUIDs and server acks.

## Findings

### Critical - fixed in current patch

Problem: repeat join could load the world but leave `Ref.main.loaded=false`. Restore and state send paths required `_can_sample_player()`, which required `Ref.main.loaded=true`. Result: the client saw the world, but the server never got a valid active `peer_state`; block actions failed with `peer_not_in_instance`.

Fix:

- `_can_sample_player(require_main_loaded := true)` now allows network paths to ask for `false`.
- Network restore/state paths use `_can_sample_player(false)`.
- After server-world `enter_game()`, if vanilla leaves `Ref.main.loaded=false`, the mod logs it and forces `Ref.main.loaded=true` for the network session.

### Critical - fixed in current patch

Problem: gameplay was unlocked after sending client state, but before the server had confirmed that the state was registered. This allowed a race: client could send block/drop actions before the server had `peer_states[sender_id]`.

Fix:

- Added server ack `confirm_client_state_registered`.
- Added `_accept_client_state(sender_id, ...)` so reliable and unreliable state RPCs both use an explicit sender id instead of relying on nested RPC-handler side effects.
- Added client flags:
  - `client_server_state_confirmed`
  - `client_server_state_confirmed_sequence`
  - `client_server_state_confirmed_instance_key`
- `_is_client_gameplay_locked()` now stays true until the server confirms state registration.
- Server confirms only when state is active and has a non-empty dimension instance key.

Audit note: `_finish_guest_character_restore()` must reset reconnect/status flags only inside the client branch. A bad indentation here can leave repeat-join state half-reset and must be caught by syntax/build checks before deployment.

### Critical - fixed in current patch

Problem: some locked client hooks returned `false`. In a hooked vanilla action, `false` can mean "let original singleplayer code continue", creating local-only blocks/drops/effects.

Fix:

- Added `_consume_locked_client_action()`.
- While connected to a server but not confirmed, world-mutating actions are consumed and status becomes `Waiting for server`.
- Applied to block place/break, drop/pickup, water/fire, entity/player attack, projectile-like actions, and foliage break.

### High - open

Time/weather are not audited enough. User observed weather/time changing between joins. This likely means the snapshot includes whatever the local client/server currently has, but there is no tight authoritative time/weather stream or join-time reset. Need explicit server time/weather snapshot plus periodic low-rate sync.

### High - open

Drop/mob ownership is still fragile. If block action or entity kill fails before server registration, client prediction can show local drops that cannot be picked up. Current patch prevents new locked predictions, but existing prediction cleanup and server UUID reconciliation need a targeted test.

### High - open

Chunk persistence needs a crash test. Successful server block actions already journal through `_ack_block_action`, and dirty chunks compact later. We still need a test that places blocks, kills the server process before the dirty flush, restarts, and verifies journal replay restores the blocks.

### High - open

RPC channel separation is not finished. Large reliable snapshots, reliable command/chat, reliable action acks, and unreliable movement/entity streams mostly share default channel behavior. Godot docs recommend channels so one reliable stream does not block unrelated gameplay messages.

### Medium - fixed in current patch

Dedicated boot logs still show a missing `res://console_mod/console_manager.gd` when only the multiplayer pack is deployed. It is noisy and indicates the mod split still has a stale optional dependency path.

Fix:

- Optional chat/console autoload bootstraps now check `ResourceLoader.exists()` before loading pack-local scripts.
- Multiplayer pack can boot without standalone console pack errors.

### Medium - open

Dedicated boot still touches several client-oriented vanilla paths:

- `Friends class not found, Steam may not be initialized: clearRichPresence`
- UI/tween errors during `enter_game()`

They do not currently prevent `STATUS_READY`, but they prove the dedicated profile is still not cleanly headless. Future dedicated work should wrap or bypass client UI/Steam calls during server boot.

### Medium - open

`_can_sample_player()` is still used in many places. Some are intentionally vanilla/UI-gated, but every network path must be reviewed and converted to explicit helpers:

- `_can_sample_menu_loaded_player()`
- `_can_sample_network_player()`
- `_can_share_loaded_world()`

The boolean parameter is a stopgap, not the final readable API.

## Test matrix before MVP

Minimum repeatable tests:

1. Fresh client process, join dedicated server, move, place block, break block, pick up drop.
2. Leave to menu, join again in the same client process, repeat test 1.
3. Do test 2 three times in a row. Logs must not contain `peer_not_in_instance`.
4. Place 3 blocks, wait 5 seconds, leave, rejoin. Blocks must still exist.
5. Place 3 blocks, force-kill dedicated process before dirty flush, restart. Blocks must restore from journal.
6. Kill a mob, pick up loot. Loot must have a server UUID and be collectible exactly once.
7. Join, observe time/weather for 2 minutes. Client must follow server, not local drift.
8. Singleplayer world list must not show server cache saves.
9. Singleplayer load/save/exit must work without `Leaving server` UI.
10. Two clients: player A drops item, player B sees and picks it up once.
